Competition handoff study

Three candidates · four states · rosters of 8, 40 and 280 · measured live

What this study is for

docs/COMPETITION_STATE_AND_RECITER_HANDOFF_RESEARCH.md proposed five directions. This study builds three of them. Direction E, the continuity component, is not a candidate here: it is applied to all three as a fixed constraint, so that any difference measured below is attributable to layout rather than to the participant block changing shape between stages. The progressive drawer was dropped, and the reason is recorded under What was not built.

Nothing here is an implementation specification. The numbers under each frame are measured from the live DOM on every render, the same technique docs/running-order-study.html uses, so a claim in the comparison table can be checked by resizing the window rather than trusted.

What the code says, before any design argument

  • EvidenceThe next reciter’s name is rendered at 10px. .competition-start-reciter > span in global.css sets font-size: 10px, max-width: 225px, overflow: hidden, and a color-mix at 72% opacity. The most important identity fact in the waiting state sits below the 12px floor rule 8 states, below the 14px minimum for anything read mid-recitation, truncated, and at reduced contrast. Making the name dominant is a correction, not a preference.
  • EvidenceThe rail and the dialog disagree about the number. CompetitionIdlePanel prints next.number raw; every other surface calls participantNumberLabel, which pads to roster width. Participant 1 reads 1 · Ahmed Rasheed in the rail and 01 in the dialog.
  • EvidenceA missing judge does not block, and burns a question. StartDialog shows No judge assigned but still advances to the board. drawPosition dispatches RECORD_DRAW before calling prepareWithQuestion, which returns early when assignment is null. The position is consumed by spentPositions and nothing else happens. That is a defect to log separately; the design below only shows what blocking would look like.
  • EvidenceSearch does not exist at a roster of 8. shouldOfferSearch is roster.length > 8. The 8 case below therefore renders without a search field, because the app has none there.
  • EvidenceCandidate B changes a state contract. visibleRosterGroups excludes the recommended participant from the list. A single ledger whose first row is the recommendation requires that exclusion to change. It is a small reversible change to a pure function, but it is not free, and it is named here rather than smuggled into a visual review.
  • InferenceRepetition is doing the work of continuity. Competition, judge and criteria are restated at each stage because the participant block is not stable enough to carry recognition on its own. This is an interpretation of the five different participant geometries in the code, not something the code states.

How they compare

Measured on the current state, roster size and viewport. Words counts visible text. Repeats counts facts said more than once in the same frame: participant name, judge name, competition name, and the waiting count. Before is the number of focusable controls a judge passes before reaching the primary action in DOM order, which is also keyboard order. Small targets counts interactive elements under 44px, the app’s own floor, which is stricter than the 24px WCAG 2.2 minimum. The numbers are zero until the page is opened in a real browser; layout measurement needs layout.

Against the grammar

DESIGN_GRAMMAR.md asks that a proposed screen state which rules it keeps and which it bends. All three candidates keep rules 2, 3, 5 and 7, and all three fix an existing break of rule 8 by raising the participant number from 11px and the reciter name from 10px onto the scale.

  • Rule 6, say it once All three remove the repeated judge and criteria block from the hot path and put it behind one disclosure. In the current build the judge name and the criteria list are stated in the idle rail (CompetitionIdlePanel) and stated again in the dialog (StartDialog) and a third time in the prepared rail (PreparedSidebar); the waiting count appears in the rail, again in reciter-queue-summary, and again in every group header. The Repeats column is the mechanical version of that count, within a single frame.
  • Rule 10, 44px during a live recitation Candidate B looks the most compact and is not: the row is the target, so its hit area is 44px even where the type is 12px. The Small targets column checks this rather than trusting it.
  • Rule 1, the page is the evidence Candidate C spends the most horizontal room, which is the strongest argument against it. At 1024×768 it is competing with the Mushaf for the same region.
  • The open violation The shell already overflows by 69px at 1024×768, and who owns viewport height is unresolved. Every frame above is clipped to the real budget so that this is visible rather than assumed.

What was not built, and why

The progressive command drawer was dropped. It proposes taking room from the same region the Mushaf occupies, in a shell that is already 69px over budget at 1024×768 with an unresolved question about who owns the viewport height. Tested now, it would produce a verdict about the shell rather than about the drawer. It is worth revisiting once the setup-flow work settles that question, and not before.
