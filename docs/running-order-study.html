The running order dialog

Between reciters, a judge opens a dialog to pick who recites next: 8 to 40 people grouped by division, one of them recommended, any of them reachable out of order. This studies four shapes for that list, each a working prototype rather than a picture of one, and each measured at both ends of the roster it has to hold.

01

The problem

The dialog held 534px of running order inside a 310px window with no scroller at all, so the last people in the order did not exist as far as a judge could reach — rule 7's test exactly. That clipping is now fixed. What it exposed is not: the list still has to hold anywhere from 8 to 40 people, and nobody had measured what any candidate shape does at the top of that range rather than the bottom.

Rows also read “Under 14 · Hifz · Hifz”, because the division is already named for its category and the category was printed again after it — the rule 6 duplication this file's sibling study found in the question board too. That is fixed; the candidates below do not reproduce it. A second, quieter repetition remains: each row also carries the institution, the division and the side, restating the division a group header above it already gives.

Every candidate below renders the same eight people, from the same judge's device strip to the same recommended reciter, so the shapes can be compared rather than described. A toggle swaps the roster to 40 so each candidate can be measured at the size that actually breaks things.

02

Four candidates

Each card is live. Choose question commits the recommended reciter in one action; Select picks anyone else out of order; Not here marks someone absent, moves them out of waiting, and updates the counts on the spot. The height caption under each card is measured at run time with getBoundingClientRect(), not typed in by hand.

All four cards share one roster. At 8 it is the real judge-1 order below; at 40 the extra people are generated across the same four divisions so the shape, not the data, is what changes.

How they compare

Heights below are measured once at load, at rest (nothing selected, nothing marked not here), for both roster sizes at once, using the same code that runs the prototypes above. Action counts are captured the same way: a script drives the real buttons and inputs and counts what actually fires, then resets the card to zero. “Fits 560px” is the dialog body budget quoted in the fact strip above.

04

Against the grammar

Every rule is one the app already keeps somewhere; the question is which ones each candidate bends, and why. Numbers below are the ones measured on this page.

A — Grouped list, as-is tightened

Keeps

  • Rule 2 — one row is one control; there is no second place to point to choose the same person.
  • Rule 6 — the division prints once, in the header; rows no longer restate it.
  • Rule 10 — Select and Not here both clear 44px, the same as every other candidate here.

Bends

  • Rule 7 — nothing here caps its own height, so it is the candidate most likely to need the dialog's own scroller to stay reachable at 40, exactly the failure that started this study.
  • Rule 1 — at 40 the list becomes the single tallest thing on the page it sits in, chrome competing for room the way rule 1 says it should not.

B — Two columns

Keeps

  • Rule 7 — the right column scrolls internally, so the last person in a 40-person order is always one scroll away, never clipped off with no scroller at all.
  • Rule 2 — the recommended reciter has exactly one fixed home; it cannot be confused with a row in the list beside it.

Bends

  • Rule 1 — two columns is more structure than eight or even forty names strictly need; the frame around the list is doing more work than the plain list in A.
  • Rule 6 — a fixed-height column that never grows does not itself say how long the order is, so the counts line has to say it instead.

C — Table

Keeps

  • Rule 7 — the scroll body and sticky group rows keep every person reachable regardless of roster size, the same guarantee as B.
  • Rule 8 — row height and padding stay on the 4px grid even as the table gets denser than any other candidate.

Bends

  • Rule 1 — a table is the most chrome-like of the four shapes; nothing else in the app reads as a spreadsheet, so this page asks a judge to learn a new pattern for one dialog.
  • Rule 10 — table density pushes toward the smallest comfortable action buttons of the four; they are held at 44px here, but there is less room to spare than A, B or D give up without a fight.

D — Search first

Keeps

  • Rule 1 — the shortest card at either roster size by a wide margin; almost none of the dialog's room goes to chrome around the decision.
  • Rule 6 — nothing is shown until it is needed, so there is nothing on screen to over-explain.

Bends

  • Rule 4 — picking someone out of order now costs a name typed character by character plus a tap, not the one deliberate gesture rule 4 asks for elsewhere.
  • Rule 7 — reachable only in the technical sense: a person whose name or number the judge cannot recall is not unreachable by the letter of the rule, but is not found either.
